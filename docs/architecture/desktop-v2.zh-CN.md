# Troy 2 桌面架构

状态：已随 v2.0 发布，Swift v1 代码已从主分支移除（可在 v1.x 标签找回）。[README](../../README.zh-CN.md#development) 说明如何构建和运行。本文最初作为提案撰写，目标是在同一仓库维护一个本地桌面应用，为 macOS 和 Windows 分别构建安装包。现有 Swift v1.4 提供行为基线。第一阶段验收工程骨架、数据链路和桌面生命周期，界面视觉在两端跑通后定稿。

## 用户在两端得到什么

| 行为       | macOS                                      | Windows                                                          |
| ---------- | ------------------------------------------ | ---------------------------------------------------------------- |
| 常驻入口   | 菜单栏直接显示所选品种、价格和时效标记     | 通知区域图标，悬停看所选报价，点击菜单切换品种或打开窗口         |
| 监控与提醒 | 四品种独立阈值，保留系统通知与已有降级提示 | 支持设置阈值，在窗口和托盘菜单查看最近一次触发。首版无需系统弹窗 |
| 窗口与进程 | 关窗继续采集，菜单可显式退出               | 相同。重复启动唤回现有实例                                       |
| 安装目标   | macOS 14+，Intel 与 Apple Silicon 通用 DMG | 首版以 Windows 11 x64、WebView2、NSIS 安装包为验收基线           |

两端都保留工行、招行黄金账户、上金所、国际金价，支持近 30 分钟走势、原始价格、人民币克价和相对波动。上金所标识官方延时。四个黄金品种独立采样，美元兑人民币只用于换算。提醒比较使用各品种的原始报价单位。

## 技术选择与目录

采用 Tauri 2。主窗口用 TypeScript 和 React，常驻采集及存储用 Rust。窗口隐藏、重开或刷新时，行情任务和阈值状态都由同一个桌面进程持有。两个平台共享一套核心和一个主窗口，各自只实现操作系统交互。初期用两个 Rust crate，一个可脱离桌面运行的核心，一个 Tauri 宿主。

```text
Cargo.toml                       Rust workspace（crates/troy-core、src-tauri）
package.json                     前端开发、检查与 Tauri CLI 入口
src/                             React + TypeScript 主窗口（pages、components、hooks、lib、i18n）
src-tauri/
  Cargo.toml                     依赖 troy-core
  tauri.conf.json                应用标识、窗口、平台打包设置
  src/
    main.rs                      注册查询与用户操作，管理菜单栏、托盘、通知和窗口生命周期
crates/troy-core/src/
  feeds.rs                       数据源请求、解码、来源与降级
  market.rs                      品种、时效、单位换算与 OHLC
  monitor.rs                     单品种采集调度、阈值与快照
  storage.rs                     SQLite、配置及迁移事务
crates/troy-core/tests/          行为测试、脱敏行情与旧库夹具
.github/workflows/               双系统验证（ci.yml）与同版本发布（release.yml）
```

两个 Rust crate 和前端分别使用固定依赖锁文件体系（Cargo workspace 共用一个 Cargo.lock，前端使用一个包管理器锁文件）。产品名称、狗狗图标、MIT 许可证和仓库地址沿用。

## 一条报价如何抵达两个桌面

1. 核心为每个品种维护一个在途请求。国内银行默认每 5 秒查询，大华与汇率每 60 秒，上金所延时行情每 30 秒，国际黄金每 10 秒。可单独为一家银行选择 3、5 或 10 秒。每个采集任务失败时独立将间隔翻倍，最长 300 秒，成功后恢复该任务当前配置的间隔。招行按客户买入价判断阈值。保留上金所分钟序列及其失败时回退到本地采样的逻辑。唤醒后重新取价，不补造休眠时段的采样。
2. 所有数据源输出统一报价，包括品种、原始价格、单位、来源、观察时间、发布时间或交易日，以及备用源与日参考价标记。区分最新、延时、过期、缓存和错误。报价失败时保留上次价格并显示状态。
3. 核心维护最新值、可绘制样本和每品种阈值状态。新鲜度合格的报价首次达到或跌破阈值时产生一次事件，高于阈值才重新启用。事件与触发状态一同持久化，重启不会仅因重读缓存而重复提醒。数据库写入失败时仍可查看报价，同时标记存储故障。
4. 桌面宿主直接订阅核心，更新菜单栏或托盘。前端通过 Tauri 命令取快照、查历史、切换品种和设置阈值，随后接收带版本序号的更新。窗口订阅和首个快照交接时按序号去重，重开窗口可从快照恢复。前端不直接访问数据源或 SQLite。

## v1.3 用户如何升级

Mac 保留现有应用标识。首次运行 v2 时，通过只读 SQLite 事务读取旧库的一致快照（含 WAL），写入独立的 v2 数据库。旧库中的 latest、samples、来源、可绘制标记和时间戳均需映射。Swift Codable 报价载荷里的日期与 SQL 表列使用不同纪元，分别解码并用同一条报价核对。导入 UserDefaults 中的 menuMarket、limit._、below._ 和已有图表偏好。导入在事务内记录版本；中断后可重试，完成后重启不得重复导入。保留原库供回退使用。Windows 首次启动创建空库。

## 迁移次序与验收

| 阶段               | 交付                                                               | 通过条件                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 · 双端骨架       | Rust workspace、Tauri 宿主、仅含报价与状态的最小窗口               | 两端从同一提交启动；使用固定报价切换四个品种；关窗后菜单栏或托盘继续更新，显式退出后停止                                                                                  |
| 2 · 行情与数据迁移 | 接入真实行情、SQLite、阈值与换算                                   | 以固定输入对照 Swift v1.3 的 K 线、重复采样、延时、过期、断网与备用源行为；验证旧库迁移、失败重试、阈值回升再触发和重启去重。在线冒烟另做，避免第三方服务波动阻断单元测试 |
| 3 · 安装与发布     | macOS 和 Windows 原生 runner 分别构建；同一候选版本产出 DMG 和 EXE | 两端完成安装、启动、驻留与退出验收，Windows 验证 WebView2 安装路径；Mac 验证菜单栏与通知权限。两个安装包和校验文件齐备后才发布同一 GitHub Release                         |
| 4 · UI 定稿        | 用两个可安装版本评审主窗口、菜单、托盘与图表                       | 确认信息层级、字号、线宽、主题与系统交互，再切换正式发布入口                                                                                                              |

v1.3 的发布流水线继续服务维护版本。v2 验证工作流仅检查构建与测试。后续发布前再确定标签规则，避免与 v1 工作流冲突。公测安装说明需如实标注 macOS 签名与公证、Windows 签名状态。完成两端安装验收后再发布 v2 正式版。
